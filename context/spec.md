# Cloudstash Intent Layer — Spec

This document specifies the composition and lifecycle of Cloudstash's Intent
layer. It builds on [requirements.md](./requirements.md). Subsystem contracts
live in child nodes.

## Status

Active.

## Scope

Defines the branch architecture, artifact ownership, identifier scheme,
maturity rules, and precedence among documentation surfaces. It does not
replace implementation-owned API schemas, event definitions, migrations, or
runtime configuration.

## Branch Architecture

The following manifest is exhaustive for core Intent nodes; enforcement requires
both core artifacts at every listed path.

```text
context/
  01-product/                    product experience, positioning, plans, privacy
  02-system/                     technical system
    01-data/                     control/content planes, events, materialization
    02-auth-and-tenancy/         identity, workspace access, roles, API keys
    03-sync/                     LiveStore clients and SyncBackendDO
    04-ingestion/                capture paths, queue, dedup, durability boundary
    05-link-processing/          metadata, content, AI, tags, notifications
    06-retrieval-and-agent/      search, export/API reads, chat tools
    07-integrations/             Telegram, Raycast, Chrome, X, public API
    08-billing-and-entitlements/ Stripe state, tiers, capabilities, usage limits
    09-account-lifecycle/        signup, approval, logout, deletion
    10-verification/             unit, data, Worker E2E, wire and bundle checks
  03-operations/                 Cloudflare resources, resilience, observability
  04-delivery/                   repository, vendoring, builds, releases, migrations
```

Numeric prefixes provide reading order within one level. A higher-numbered node
may depend on a lower-numbered sibling; lower-numbered nodes should not depend on
higher-numbered mechanisms.

## Artifact Ownership

| Artifact            | Owns                                                                       |
| ------------------- | -------------------------------------------------------------------------- |
| `vision.md`         | Need, desired future, exclusions, durable success criteria                 |
| `requirements.md`   | Assumptions, external constraints, accepted tradeoffs, testable guarantees |
| `spec.md`           | Current system shape that realizes the requirements                        |
| `ontology.md`       | Canonical terms and their relationships                                    |
| `intuition.md`      | Narrative mental model and map to formal artifacts                         |
| `.decisions/`       | Consequential accepted choices, evidence, and rejected alternatives        |
| `.delta/`           | Confirmed current divergence between Intent and reality                    |
| `open-questions.md` | Unsettled design questions with a blocker                                  |
| `roadmap.md`        | Non-binding future direction                                               |
| `.experiments/`     | Evidence generated by this project                                         |
| `.reference/`       | Relevant external facts and source snapshots                               |

All companion artifacts are lazy. Do not create empty template directories.

## Authority and Precedence

Per [decision 0001](./.decisions/0001-adopt-single-intent-layer.md):

1. `context/` is the only always-current durable intent source.
2. Source code, tests, schemas, migrations, and configuration own executable
   truth. A disagreement with Intent is recorded as a delta until one side is
   deliberately changed.
3. `docs/architecture/` and `docs/features/` teach or explain and must derive
   durable claims from the owning node.
4. `docs/incidents/` and accepted PRs preserve historical evidence; they do not
   automatically describe current behavior.
5. `docs/todos/` and `docs/kanban.md` own plans and status, never durable system
   truth.
6. `README.md` owns repository onboarding. `CLAUDE.md` and `AGENTS.md` own agent
   procedure and point to this layer rather than duplicating it.
7. Landing and legal pages are deployed product surfaces. They must agree with
   product requirements, but their copy is not the source of those requirements.
8. `vendor/livestore/context/` belongs to the upstream LiveStore submodule and
   is outside the Cloudstash Intent corpus.

Known migration drift is tracked in
[DELTA-001](./.delta/DELTA-001-legacy-documentation-authority.md).

## Node Conventions

- Every node has `requirements.md` and `spec.md`; other artifacts are lazy.
- A child references parent requirements with a backticked
  `` `refines: <ID>` `` marker instead of restating them. Refinement edges must
  point to an ancestor or an earlier node in the declared numeric reading order,
  never forward to a later mechanism.
- `vision.md` and `requirements.md` are protected. Changing goals or guarantees
  requires explicit maintainer confirmation recorded in the PR.
- Every `spec.md` links to its sibling requirements and declares one status:
  - `Draft` — proposed or incomplete contract; it may not be cited as current
    behavior without a maturity marker or delta;
  - `Active` — current authoritative shape, with known divergence represented by
    linked open deltas;
  - `Stable` — Active and deliberately slow-changing, with complete boundary
    verification and no known material divergence.
- Unimplemented proposals do not appear as current spec. They belong in
  `roadmap.md`, `open-questions.md`, or the planning system. A current product
  surface that falsely advertises one is described by a delta, not as a
  realization.
- Experimental behavior with real code is introduced by a bold
  `**Maturity: experimental**` marker.
- Companion directories are lazy and must contain at least one valid record.
- Resolved deltas are deleted; Git history is the archive.

## Decision and Delta Lifecycle

Accepted decisions use the current Intent decision format: `Context`, `Evidence
and Argument`, at least two principled `Options` with tradeoffs, and `Decision`.
Proposals may exist under `.decisions/.proposed/` on a branch but must be
accepted, folded into another artifact, deferred, or deleted before merge.

A delta must identify the divergence, link both Intent and implementation
evidence, choose `update implementation`, `update Intent`, or `decide`, and name
a concrete resolution signal. Open deltas may merge because they describe known
reality; closed delta files may not.

## Enforcement

The project-native deterministic checker lives at
[`tools/intent`](../tools/intent/) and runs through `bun run check:intent`. It
checks declared node pairs, corpus presence, links, IDs, node namespaces,
ancestor refinements, spec status, companion directory/record shapes, maturity
markers, evidence links, and proposed-record hygiene. It checks decision shape,
not argument quality. Requirement testability, spec completeness, rationale,
and delta freshness remain maintainer/agent judgment.
